## 1. 问题定义与流水线分层定位 (Problem Statement & Positioning)

在自动化演示文稿生成领域，业界最常犯的根本性错误是**“试图让大模型一步到位：从万字长文直接吐出带 HTML 排版的成品 PPT”**。这种设计必然导致模型注意力崩溃（Attention Collapse）：
* **上游迷失**：长文篇幅巨大，大模型在梳理逻辑脉络的同时还要心算像素坐标与字号，导致提炼出的要点东拼西凑、丢失主线；
* **单页过载**：大模型往往偷懒将整段叙述文字直接作为列表输出，产出单页 300~500 字的“论文式长文幻灯片”；
* **节奏崩塌**：缺乏全局演说节奏感，关键论点与细枝末节平铺直叙，既没有起承转合，也没有留白呼吸。

因此，`markdown2slide` 确立了严格的**流水线职责分层与关注点分离（Separation of Concerns）**：

| 流水线阶段 | 核心智能体 | 唯一职责 | 绝对红线 (Redlines) |
| :--- | :--- | :--- | :--- |
| **Stage 1 (本规范)** | **长文提炼与节拍智能体** (Distiller & Pacer) | **长文信息蒸馏与演说节奏编排**：提取核心论点、消除冗余、划分单页节拍、生成未排版的纯净 Markdown 初始草稿 | **严禁生成任何 HTML 标签**、严禁书写 `style`、严禁考虑字号与边距 |
| **Stage 2 (下游)** | **后处理排版智能体** (Layout & Healing Agent) | **视觉容器装配与视口几何闭环**：基于 CDRD 响应式断点装配语义网格与卡片，通过无头沙盒测量进行 3 轮闭环自愈 | **严禁主观删改**作者的核心教学论点与代码逻辑，仅负责排版重塑 |

## 2. 篇章修辞结构分析与论据逻辑树 (Discourse Parsing & RST)

长文提炼的核心不是“文字摘要（Summarization）”，而是**“论辩逻辑与演说结构的重构（Argument Reconstruction）”**。

智能体必须基于**修辞结构理论（Rhetorical Structure Theory, RST）**将输入的 Markdown 长文解析为树状认知模型：

```
                    ┌────────────────────────────────────────┐
                    │      长文全篇核心主旨 (Core Thesis)     │
                    └───────────────────┬────────────────────┘
                                        │
             ┌──────────────────────────┴──────────────────────────┐
             ▼                                                     ▼
┌─────────────────────────┐                               ┌─────────────────────────┐
│  主干议题一 (Section 1)  │                               │  主干议题二 (Section 2)  │
└────────────┬────────────┘                               └────────────┬────────────┘
             │                                                         │
   ┌─────────┴─────────┐                                     ┌─────────┴─────────┐
   ▼                   ▼                                     ▼                   ▼
[核部: 核心论点]   [卫星部: 论据]                         [核部: 机制推导]    [卫星部: 实验数据]
(必选保留)         (浓缩为要点)                           (必选保留)          (提炼为对比卡片)
```

### 2.1 核部（Nucleus）与卫星部（Satellite）分离法则
1. **核部抽取（必须上墙）**：
   - 作者的核心论断、第一性原理推导、关键定义、系统架构主线、关键代码实现；
   - 核部文字构成了幻灯片的**主标题（H2）**与**第一视觉引导语**。
2. **卫星部蒸馏（浓缩或舍弃）**：
   - 叙述性铺垫、背景回顾、口语化连接词、次级修饰从句、宽泛的文学隐喻；
   - 卫星部中的有效支撑材料（定量数据、对比案例、注意事项）必须经过**短语化（Phrasing）**重塑，转化为不超过 4 条的精炼 Bullet。

### 2.2 四大演讲原型模式识别 (Archetype Classification)
智能体在解析每个小节时，必须识别其属于哪种演说原型，并在输出草稿中注入对应的语义意图标记：
* **[概念界定型]**：核心术语 $\to$ 核心特征 $\to$ 解决的痛点；
* **[双向对比型]**：方案 A vs 方案 B $\to$ 核心维度对照 $\to$ 选型权衡；
* **[流程机制型]**：输入原料 $\to$ 处理管道 $\to$ 阶段产物 $\to$ 终极收敛；
* **[代码实践型]**：核心逻辑片段 $\to$ 关键参数解析 $\to$ 预期执行效果。

## 3. 演说节奏节拍器与幻灯片容量预算 (Pacing & Capacity Budgeting)

优秀的演讲幻灯片具有呼吸感与起伏节奏。长文提炼智能体通过数学模型控制单页容量与整篇节奏。

### 3.1 目标幻灯片页数动态推导公式

根据长文有效字数 $W$、章节结构密度 $S$ 与目标演说深度，动态规划总页数预算 $N_{\text{slides}}$：

$$N_{\text{slides}} = \text{clamp}\left( \left\lceil \frac{W_{\text{effective}}}{180} \times \alpha \right\rceil, \ N_{\min}, \ N_{\max} \right)$$

* $W_{\text{effective}}$：剔除空行、代码注释与纯引用后的有效字数；
* $\alpha$：信息密度衰减系数（普通文章取 $0.75$，技术深度专著取 $0.9$）；
* 默认上限约束：单节长文通常收敛在 $12 \sim 25$ 页之间，杜绝“无限切片”导致听众认知疲劳。

### 3.2 五步递进认知节奏（The 5-Beat Pacing Rhythm）
对于单篇长文或主题模块，智能体按照五步认知律进行幻灯片宏观排期：
1. **Hook（悬念引入）**：提炼现状痛点、认知冲突或核心挑战（1~2 页）；
2. **Context（背景基准）**：锚定前置认知与核心边界（2~3 页）；
3. **Core Thesis（机制解构）**：主论点推导、系统架构全景展示（3~5 页）；
4. **Deep Dive（深度证据）**：代码实验、性能数据、方案对比与边界踩坑（4~8 页）；
5. **Takeaways（总结提炼）**：方法论金句、行动清单与落地结论（1~2 页）。

### 3.3 单页容量硬预算（Single-Slide Budget Cap）
为了确保下游 Stage 2 排版智能体能够 100% 优雅自愈，Stage 1 必须严守**单页输入预算上限**：
* **主标题（H2）**：$\le 18$ 汉字（简明有力，拒绝复合从句）；
* **核心导语（Sub-headline）**：$\le 35$ 汉字（直击本页核心主旨）；
* **正文列表（Bullets）**：$\le 4$ 条，单条 $\le 28$ 汉字（每条必须包含 `**加粗引导词**`）；
* **代码块（Code Snippet）**：$\le 8$ 行代码，单行 $\le 45$ 字符（只保留核心函数调用，剥离样板代码）；
* **整页有效汉字总量**：严格拦截在 **180 汉字以内**。

## 4. 长文到演示文本的重构工序 (Information Distillation Pipeline)

智能体执行 5 步递进工序，将非结构化长文转换为标准 Marp 初始草稿：

```
[原始 Markdown 长文]
       │
       ▼ (Step 1: 文档语义树解析)
 [ 识别章节骨架 / RST 核心论点抽取 ]
       │
       ▼ (Step 2: 演说节拍切片与拆页)
 [ 注入 '---' 幻灯片强制分页符，分配各页认知目标 ]
       │
       ▼ (Step 3: 段落重写与信噪比蒸馏)
 [ 消除从句冗余，重塑为“主谓宾/加粗引导词” ]
       │
       ▼ (Step 4: 语义意图与场景标记)
 [ 注入意图提示 <!-- layout: compare / code / insight --> ]
       │
       ▼ (Step 5: 契约校验与输出交付)
[零内联、纯净 Marp 初始草稿 (.raw_draft.md)]
```

### 工序 1：文档语义树解析 (Document AST Parsing)
- 解析输入长文的 Markdown 标题层级（H1/H2/H3）；
- 将连续叙述的自然段落按“话题转换点（Topic Shift）”聚合为语义块。

### 工序 2：演说节拍切片与拆页 (Beat Slicing)
- 使用 `---` 作为单页幻灯片之间的天然语法边界；
- 每个页面必须且仅能承担 **1 个独立的认知目标**；若一个二级标题包含 3 个并列论点，强制拆分为 3 页连贯幻灯片。

### 工序 3：段落重写与信噪比蒸馏 (Rewriting & High SNR)
- **动词前置化**：将“我们通过对系统的缓存机制进行了深入的优化从而使得吞吐量提升”重写为：“**缓存机制深度优化**：重塑命中链路，系统吞吐量提升 300%”；
- **视觉锚点植入**：为每一个论点配置核心引导词并加粗，引导受众视线。

### 工序 4：语义意图标注 (Semantic Intention Annotation)
在单页草稿中，智能体不写任何 HTML，但可以通过简洁的标准 Markdown 注释向下游传递视觉装配意图：
- `<!-- intention: comparison -->`：提示下游使用双栏对比网格；
- `<!-- intention: code-walkthrough -->`：提示下游使用图文代码分栏；
- `<!-- intention: key-takeaway -->`：提示下游使用强调洞见卡片。

### 工序 5：契约校验 (Schema Verification)
- 运行字符计数器，校验单页汉字是否 $\le 180$ 字；
- 确认全篇没有任何 `<div style="...">` 等脏代码，正式交付下游。

## 5. 智能体系统提示词工程与输入输出契约 (Distiller Agent IPO Spec)

### 5.1 系统提示词规范 (System Prompt Specification)

```markdown
你是“markdown2slide 长文到演示要点提炼架构师智能体 (Stage 1 Distiller & Slide Pacer)”。
你的唯一职责是：接收任意格式的长篇 Markdown 文档（技术文章、教材章节、学术论文、行业研报），基于认知负荷理论与演说修辞结构，将其提炼、解构并重写为节奏清晰、要点精炼的“Marp 原始演示草稿 (Raw Draft)”。

【绝对禁令 (Hard Redlines)】
1. 【严禁编写任何 HTML 标签与 CSS 样式】：绝对禁止输出 <div>、<span>、style="..."、<style scoped> 等任何前端排版代码。排版完全由下游智能体负责；
2. 【严禁全盘大段照抄原文】：必须对散文式段落进行信噪比提炼，消除口语连接词与冗余修饰，重构为高密度的动宾短语与加粗要点；
3. 【严禁单页容量超标】：单页正文汉字严格控制在 180 字以内。遇到多要点长篇幅，必须坚决使用 '---' 拆页；
4. 【严禁无中生有与幻觉】：必须忠实于原文的核心论点、实验数据与代码逻辑，杜绝主观捏造事实。

【提炼与重写工序】
1. 结构化解构：提取文档的核心主旨、各小节核心论断（核部）与关键数据/例证（卫星部）；
2. 节奏编排：遵循“引入/痛点 -> 核心机制 -> 深度细节/代码 -> 总结落地”的演讲认知节奏，使用 '---' 进行单页切片；
3. 单页要点蒸馏：
   - 每页必须有一个简明有力的 H2 标题（<= 18 汉字）；
   - 配备 1 句高信息密度的导语或认知冲突；
   - 提取 3~4 条原子列表项，每条必须采用“**核心引导词**：精炼说明”结构；
   - 保留核心代码块（<= 8 行）或关键指标对比；
4. 意图注解：可在页首添加一行注释标注演说意图（如 <!-- intention: comparison / code / insight -->）。
```

## 6. 真实长文提炼用例对照 (Transformation Case)

### 6.1 输入：原始 Markdown 长文（某分布式缓存技术博客片段，约 650 字）

```markdown
## 分布式缓存的高并发穿透与布隆过滤器实践

在日常的高并发大型系统架构设计中，缓存穿透是一个极为致命但又非常容易被忽视的性能陷阱。所谓缓存穿透，通常是指客户端发送了大量恶意构造或者业务上根本不存在的数据查询请求。当这些请求到达网关和应用服务层之后，缓存系统（例如 Redis 集群）在内存中必然查询不到对应的 Key。由于传统的缓存设计逻辑是“缓存未命中则回源查询关系型数据库”，这就导致所有的海量请求瞬间毫无阻挡地直接击穿了缓存层，全量压垮底层的 MySQL 等持久化存储集群，从而引发数据库连接池耗尽、慢查询堆积，最终导致整个系统级雪崩。

为了彻底阻断缓存穿透带来的系统崩溃风险，工业界最经典的防御利器就是布隆过滤器（Bloom Filter）。布隆过滤器的核心本质是一个非常高效的二进制位图（BitMap）结合多个互相独立的无偏哈希函数（Hash Functions）。当一个真实存在的键写入系统时，布隆过滤器会使用 k 个哈希函数分别计算该 Key 的哈希值，并将位图中对应索引位置的比特位全部置为 1。当外部查询请求进入时，系统首先拿着查询 Key 经过同样的哈希运算去检查位图对应的比特位：只要发现有任何一个比特位为 0，就可以 100% 绝对肯定该数据在数据库中绝对不存在，从而在内存中毫秒级拦截该请求，根本无需打到后端数据库！当然，布隆过滤器也存在一定的误判率（False Positive），即可能所有比特位都为 1 但数据实际上不存在，但通过合理设置位图大小与哈希函数数量，完全可以将误判率压制在 0.01% 以下。
```

### 6.2 输出：经 Stage 1 智能体提炼的规范 Marp 初始草稿 (Raw Draft)

```markdown
---

恶意请求穿透缓存直击持久层，是高并发架构的致命隐患：

* **穿透机理**：查询业务不存在的非法 Key，Redis 缓存层必然持续未命中；
* **回源雪崩**：全量并发穿透防护网，直接冲击底层关系型数据库 (MySQL)；
* **级联恶果**：数据库连接池瞬间耗尽、慢查询雪崩式堆积，引发系统瘫痪。

---
<!-- intention: mechanism-deepdive -->
## 破局利器：布隆过滤器的拦截原理

基于高效二进制位图 (BitMap) 与独立哈希函数，在内存层筑牢第一道防线：

* **写入标记**：Key 经 $k$ 个无偏哈希运算，将位图对应索引位全部置为 1；
* **零回源拦截**：查询时若任一比特位为 0，**100% 判定数据不存在**，就地拒绝；
* **误判率控制**：存在微小误判（False Positive），合理规划参数可压制在 0.01% 以下。

---
<!-- intention: comparison -->
## 方案抉择：布隆过滤器 vs 传统空值缓存

根据数据分布规模与一致性要求进行工程权衡：

* **空值缓存方案**：实现极简，但大量无效 Key 严重浪费内存，存在时效滞后；
* **布隆过滤器方案**：空间效率极高（千亿级数据仅需数 MB），只读毫秒拦截；
* **推荐实践**：海量稀疏请求前置布隆拦截，高频热点辅以短期空值缓存兜底。
```

> 2. 单页正文字数全部收敛在 **70~110 汉字**以内，没有任何孤立的冗余长句；
> 3. 全文 **0 HTML 污染**，语义意图标注清晰，作为输入交付下游 Stage 2 排版智能体时，可被完美映射为两栏网格、洞见卡片与对比卡片，达成 100% 自适应美观呈现！

## 7. 质量门禁与验收指标 (Quality Gates)

在交付给下游 Stage 2 之前，Stage 1 的产出物必须通过以下质量门禁：

1. **零 HTML 侵入率 (Zero-HTML Rate = 100%)**：
   - 输出文本中严禁包含 `<div`、`<style`、`style="`、`<span>` 等任何 HTML 标签，语法违者打回重提。
2. **单页容量硬指标 (Capacity Compliance = 100%)**：
   - 单页有效汉字总量严格 $\le 180$ 汉字；
   - 单页列表项严格 $\le 4$ 条，单条长度 $\le 28$ 汉字。
3. **核心信息保留率 (Information Recall $\ge 90\%$)**：
   - 长文中的核心论点（核部）、关键术语定义与重要数据必须被完整继承，不得发生信息断层。
4. **分页合理性与演说节奏度**：
   - 严禁出现连续两页同一议题未作区分的情况；多步机制必须在主标题中通过“(一)/(二)”或递进命名明确标注。
